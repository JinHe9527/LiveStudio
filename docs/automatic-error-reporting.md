# 错误记录与离线诊断包

## 当前交付边界

使用者已选择无需服务器、无需额外账号的方案。v0.1.33 增加“设置 → 错误诊断 → 导出诊断包”：在出问题的电脑上导出 ZIP，通过 QQ 或微信发给开发者。导出不需要 Agent 连接成功，也不进行网络请求。发布状态以 GitHub Release 为准。

包内固定包含 `说明.txt`、`summary.json`、`errors.json`。通过重新序列化已验证的错误记录生成，不直接压缩日志目录。兼容摘要仅保留检查时间、应用版本、结构哈希、已知状态和字段/差异数量；不复制原始提示、路径、参数或适配标识。检测结果来自当前会话最近一次检测，尚未检测时可为空。

空日志也能导出，说明中明确“无错误记录不代表通过测试”；损坏、不可读取、过大或超出数量上限的记录以跳过数量标注。导出不会删除日志或把日志标记成已提交。选取保存位置后取消会保留所有原记录。

测试者发送 ZIP 时请另行说明：操作步骤、预期结果、实际结果、大致发生时间。开发者据此复现和修复，并在原失败电脑复测；诊断包不能替代真机验收。

此前实现的 GitHub 接收端仍保留，但**尚未部署或开通自动提交**。发布变量未设置时，设置页隐藏自动提交开关和提交状态按钮，显示本机记录与导出说明。

默认目标为公开仓库 `JinHe9527/LiveStudio` 的 Issues。独立接收端是 .NET 10 ASP.NET Core 服务，不依赖原来已停用的 LiveStudio 云端。若选择 Cloudflare Workers，需要使用等价的 Worker 接收实现或另行托管此服务；此项目不能直接当作普通 Worker 上传。

## 客户端覆盖

- Desktop：进程未处理异常、未观察任务异常、界面已捕获的保存、恢复、导入、导出、连接、更新等操作异常；本机 Agent 连接和响应超时有独立原因码。
- Agent：启动及未处理异常、Error/Critical 日志、控制请求异常、应用检查异常、恢复返回的已知失败状态。
- RestoreCoordinator：事务失败、回滚异常及部分运行状态清理异常。诊断失败不会改变事务结果。
- Setup：安装失败先记录，退出前最多等待 5 秒提交。`--verify-only` 不启动自动报告。
- `--demo`、Desktop 的 `DOTNET_WATCH=1`、`LIVESTUDIO_LOCAL_ONLY=1` 隔离会话不启动上报。单元测试不调用进程启动入口，不访问 GitHub。

应用被操作系统直接终止、断电、尚未加载 .NET 的启动故障、日志目录完全不可写等情况不能保证留下报告。已经保存的报告可在下一次运行时重试。当前没有自动上传原始安装器 `install.log`、进程转储、截图或直播配置的功能。

## 数据与保留

报告只包含 schema、随机报告 ID、错误指纹、组件、代码操作名、LiveStudio/Windows/架构、最近已检查到的 OBS/直播伴侣版本及运行状态、次数和时间、异常类型/HResult/固定原因分类、最多 5 层异常链和每层最多 16 个代码调用位置。版本无法解析时记为 `0.0`，未完成应用检查时版本列表可为空。

**不序列化** `Exception.Message`、`Exception.Data`、异常对象或日志格式化参数；不读取账号、电脑名称、设备序列号、Windows 用户名、原生 JSON、Cookie、Token、OBS 密码、推流密钥、布局或音频。已知中文错误只在内存中映射为固定原因码，不上传原文。

本机位置：`%LOCALAPPDATA%\LiveStudio\Diagnostics`。Desktop 和 Agent 在同一用户下共享队列；以另一管理员身份安装时，Setup 的日志位于该管理员的 LocalAppData。

- 相同组件、操作、版本、原因和代码堆栈合并计数；磁盘最多保留 100 类，超过后淘汰最早更新的记录。
- 文件通过同目录临时文件、刷盘和原子替换写入；跨进程互斥。坏 JSON 不阻塞其他报告。
- 每分钟尝试最多 5 类；请求限时 10 秒。失败从 2 分钟逐渐退避，最长 6 小时。
- 提交成功后，同类后续错误最多每日更新一次。提交期间新增的次数仍保留为待提交。
- 必须收到匹配的报告 ID 和固定 GitHub 仓库的 Issue URL 才算交付成功；拒绝重定向和不可信回执。
- 设置中的开关只控制网络提交；关闭后仍保留本机诊断。已经提交的公开 Issue 不会因关闭开关而删除。

## 接收端部署

先确定托管位置；目前没有为本功能占用旧服务器、创建收费资源或上传 GitHub 凭据。

1. `dotnet publish src/LiveStudio.Diagnostics.Relay/LiveStudio.Diagnostics.Relay.csproj -c Release -o <发布目录>`。
2. 通过托管平台的 Secret 配置 `Diagnostics__GitHubToken`。使用仅授权目标仓库 Issues 写入的专用凭据；禁止写入源码、客户端安装包、命令行参数或聊天。
3. 配置 `Diagnostics__Directory` 为持久磁盘目录。运行一个服务实例；状态目录不可放在发布时会被清空的临时层。
4. 在 HTTPS 反向代理后运行，开放 `POST /reports`。`GET /health` 仅表示进程存活，不证明 GitHub 凭据有效。
5. 限制请求正文 32 KiB；接收端拒绝未知 JSON 字段、无效结构和不安全符号。每小时全局最多 60 个报告请求，超限返回 429，客户端保留队列重试。公开入口仍可能受恶意占用配额影响；正式部署应配置平台入口限流及监控。客户端不接受任意仓库或 GitHub 凭据参数。
6. GitHub API 按[官方 Issues 文档](https://docs.github.com/en/rest/issues/issues)调用，使用 `2026-03-10` API 版本。

每个指纹一个 Issue，生成区块最多保留最近 10 份不同报告，并限制正文大小；维护者在区块外的笔记会保留。每份 `occurrences` 是该本地报告的累计次数，不能当作全体电脑总数。

接收端先持久记录创建意图，再请求 GitHub。明确的 400/401/403/404/422/429 拒绝允许后续重新创建；网络中断或 5xx 等不确定结果只查找已有 Issue，不盲目重发 POST。最多核对最近 500 条 Issue；若仍无法确认，保留 503/待提交状态，由运维按状态文件指纹核对后处理。状态目录最多 5000 类，不自动删除去重依据。

## 发布与验收

- GitHub 仓库变量 `LIVESTUDIO_DIAGNOSTICS_ENDPOINT` 设置为真实 `https://.../reports` 地址。
- Release workflow 将其作为 `LiveStudioDiagnosticsEndpoint` MSBuild 属性同时注入 Desktop、Agent 和 Setup 的 Diagnostics 程序集。
- 本地发布也可通过同名 MSBuild 属性或进程环境变量注入。没有配置时仅落盘，设置页明确显示“尚未配置 GitHub 接收服务”。
- 正式发布前必须用专用服务凭据完成：模拟错误创建 Issue → 重复发送仍同一 Issue → 断网保存 → 重启联网提交 → 设置关闭后停止发送 → 两台电脑分别报告并可区分 → 更新包中的三个进程都能提交。

2026-09-15 本地自动化检查覆盖隐私投影、重启持久化、去重、容量、离线退避、关闭开关、并发新增不丢计数、无效回执、损坏文件、服务凭据缺失、重放、不同报告保留、维护者笔记保留、不确定 POST 核对和明确拒绝后重试。使用替身 HTTP，不代表真实 GitHub 或异机验收。

真实 GitHub 联调（提取本机登录凭据交给测试接收端）和随后无凭据的本机接收服务进程启动测试均被自动审批策略阻止，工具未提供更详细理由。没有创建测试 Issue，也没有启动常驻接收服务。不能把这些步骤记作通过。
